## 第一题（简答 200 分）：RSA 弱模数 p²q + 共享因子

### 题目

同一网络管理中心两个用户 A、B 的公钥（10 进制整数），公钥指数均为 D = 2^16+1 = 65537：

- A 用户 `na`（1024 bit）：`149246565442763940835722636804636671495647683848506669719961869915298101083628798493531285477223116007709554452539893432994503330326222995286026708038549027066361007538288404414093090571014304312231064397282794931931722856172212350001014197754976847189976206272816298245852465051772886548495540633832272442283`
- B 用户 `nb`（1024 bit）：`98931160587985373474392503750103526965234466159358081114879861121504177434642036801035094404162157997948803156728602180847466792629834151373662865607322327255047396266103072083670332782258386690173078828511402022500844759416392350318980777131166630835592279386987343477713492786892338159045094588897467971029`

1. 求用户 A 的私钥；
2. A 发送给 B 的加密消息 `C`，求明文（`C` 见题面，1021 bit）。

### 解析

**考点一：φ(p²·q) ≠ (p²−1)(q−1)。** na 分解后为 `na = ps² · q`，其中 `ps = 1571007745962441239`。平方因子对应欧拉函数：

```
φ(na) = φ(ps²)·φ(q) = ps(ps−1)·(q−1)
da = 65537⁻¹ mod φ(na)
```

错误写法 `(ps²−1)(q−1)` 差一个因子 ps，求出的 d 无法解密——这是本题最大的坑。

**考点二：共享素数。** `gcd(na, nb) = q` 直接把 nb 也分解了：`nb = q · r`，`r = 1636007954745804602439513446189799023`（121 bit 素数）。注意 nb 是**普通两素数**模数，φ(nb) = (r−1)(q−1)。

**考点三：明文是整数不是文本。** `m = C^db mod nb = 988193086256651455898930830071291535642038419963`（160 bit）。它不是任何编码的文本，`long_to_bytes(...).decode('utf-8')` 会报 `UnicodeDecodeError`——**答案直接填十进制串**。结果只有 160 bit（正常解密应接近模数全长 1024 bit）本身就是验证：出题人用小整数当明文。

```python
from math import gcd
ps = 1571007745962441239
q  = gcd(na, nb)                      # 共享素数直接求出
assert na == ps*ps*q and nb == q*r
da = pow(65537, -1, ps*(ps-1)*(q-1))
db = pow(65537, -1, (r-1)*(q-1))
m  = pow(C, db, nb)                   # 十进制串即答案
```

> **思路回放**：① "A 发送**给** B" → 方向用 B 的密钥对，A 的私钥只是第 1 问的产物；② 单步解密乱码时别急着怀疑密钥——四种组合（^da/^db/公钥重加密）和"先验签再解密"两条链全试仍乱码；③ **转折点是看解出结果的长度**：只有 20 字节（160 bit），而正确解密应接近模数全长 1024 bit，概率约 2⁻⁸⁶⁴ 绝非巧合——这不是乱码，就是明文本身；④ 结论：明文是小整数而非文本，`.decode()` 必炸，直接交十进制串。

**答案**：`da = 138329251029034134190055740297279753306849806801788132449703806121394625094015408384732482649387442234385186797036266211674654367261586084332141910957657835253532291335895927862742250358489887602307741988486656258534822586397293093013061619182101367261799254101085896192937959046797771948070593835439440056829`；明文 `988193086256651455898930830071291535642038419963`。

**坑位清单**：pycryptodome 的 `RSA.construct` 全程用不上（拒绝合数"素因子"，也不提供 φ）；非标准模数一律原生 `pow` + 手算 φ。

## 第二题（简答 200 分）：国密 SSL VPN 握手流量分析

### 题目

分别从两个 SSL VPN 网关采集到 2 份客户端握手数据（pcap 附件）。观察、分析、计算：

**1）关于两份握手数据，下列描述正确的是？**

- a. 数据 1 的密钥交换算法标识是 ECC，认证方式是双向认证
- b. 数据 2 的密钥交换算法标识是 ECDHE，认证方式是单向认证
- c. 客户端与服务端的密钥交换算法标识是 ECC 时，使用 SM2 算法的密钥交换协议
- d. 客户端与服务端的密钥交换算法标识是 ECDHE 时，使用 SM2 算法的密钥交换协议

**2）数据 1 的 ClientKeyExchange 消息载荷中存在计算预主密钥所需的重要数据，数据是？**

**3）当密钥交换算法标识是 ECC 时，下列说法正确的是？**

- a. 预主密钥长度是 48 字节
- b. 预主密钥长度是 16 字节
- c. 预主密钥是客户端产生的
- d. 预主密钥是服务端产生的
- e. 预主密钥是双方共同产生的

**4）当密钥交换算法标识是 ECDHE 时，下列说法正确的是？**

- a. U or V = `[(dA + x₁·rA)(dB + x₂·rB)]G`，余因子 h=1
- b. 已知双方随机数、不知私钥，可求 U/V
- c. 已知双方私钥、不知随机数，可求 U/V
- d. 已知 U/V、随机数和一方私钥，可求另一方私钥
- e. 不检测证书可完成中间人攻击

### 解析

两份包都是**国密 SSL**（record 版本 `0x0101`，GM/T 0024-2014 / TLCP）——国密体系零基础的话，先读 [国密算法入门](国密算法入门.md)：

| | 数据 1（`5873acad…` 5269B） | 数据 2（`f3b768b9…` 13451B，魔数 a1b2cd34 需手工解析） |
|---|---|---|
| ServerHello 选定套件 | **0xE011 = ECDHE_SM4_CBC_SM3** | **0xE013 = ECC_SM4_CBC_SM3** |
| 认证方式 | **双向**（服务端发 CertificateRequest，客户端回 Certificate[sm2-user-sig/enc] + CertVerify） | **双向**（同样有客户端证书 hm_userA1 + CertVerify） |
| CKE 载荷 | `03 000041 ‖ 04‖X‖Y`（65 字节临时 SM2 公钥） | DER 序列：两个 32B 临时公钥坐标 + 32B/48B 校验值 |
| SKE 载荷 | 65B 临时公钥 + 71B SM2 签名 | 仅 70B 签名 |

> **思路回放**：① 先修格式再谈内容——scapy 拒读第二份包，对比魔数：`d4c3b2a1` 标准 vs `a1b2cd34` modified pcap（每包多 8 字节附加头），手工按"16B 包头 + 8B 附加 + 数据"切包重组 TCP 流；② 解析 record：type=0x16、ver=**0x0101** → 国密 SSL，不是标准 TLS，后续全按 GM/T 0024/TLCP 解读；③ 算法标识看 **ServerHello 选定的套件号**（0xE011=ECDHE、0xE013=ECC）；④ 单向/双向不靠规范猜，**数包里有没有三个字段**：服务端 CertificateRequest、客户端 Certificate、CertVerify——两份都有 → 都是双向；⑤ CKE（握手 type=16）按结构切：`03 000041 ‖ 04‖X‖Y` 的 65 字节就是临时 SM2 公钥；⑥ 子题 3/4 与抓包无关，回归 GM/T 0024 与 GM/T 0003.3 条文推理。

**1) 答案 c。** a 错：数据 1 是 ECDHE 不是 ECC；b 错：数据 2 是 ECC 且认证方式不对；d 错：ECDHE 套件的标识就叫 ECDHE，SM2 密钥交换协议（GM/T 0003.3）专指 ECC 套件使用的协商协议。

**2) 答案（65 字节客户端临时 SM2 公钥，04‖X‖Y）：**

```
04fc57e6dbc62d06c13e87620734d806296f2d7dde9bcacfc11394275c603f149ebeb
cf5c75bb1738750ca744f0dc10cc819d615a6f80ebdf60a34dd9321dace6d
```

定位方法：Wireshark 过滤 `tls.handshake.type == 16`（国密版可手工解析：record 头 type=0x16、ver=0x0101，握手消息 type=16=ClientKeyExchange）。

**3) 答案 b、e。** ECC 套件预主密钥由双方 SM2 密钥协商**共同产生**，长度 **16 字节**（对照组：RSA 套件预主密钥 48 字节、客户端产生）。

**4) 答案 a、e。** a 就是 GM/T 0003.3 的协商公式（h=1）；b 缺私钥、c 缺临时随机数，都算不出 U/V；d 归结为椭圆曲线离散对数，不可行；e 是经典结论——ECDHE 本身无身份认证，不校验证书就能中间人。

**坑位清单**：数据 2 的 pcap 魔数被改成 `a1b2cd34`（modified pcap，每包多 8 字节附加头）——scapy 拒读，但 **Wireshark 4.x 可直读**（capinfos 报 "Modified tcpdump - pcap"，tshark/editcap 也认）：走 tshark 直接分析，走 scapy 才需要手工按"16B 包头 + 8B 附加 + 数据"切包；证书 OID `1.2.156.10197.1.301`（`2a811ccf5501822d`）= sm2p256v1 曲线，可用来确认 SM2。

## 第三题（简答 200 分）：Office 文档加密破译

### 题目

某加密系统对 office 文档加密，获取其加密密报（附件 docx，10410 字节），分析密报规律，求取加密算法，破译密报。明文内容是？

### 解析

Word/WPS 报"文档已损坏"、记事本打开乱码——**不是文件损坏，是整体被加密**。docx 本质是 ZIP：正确开头 `50 4B 03 04`（PK），结尾 22 字节是 EOCD `50 4B 05 06 …`。观察本文件：头 `fa cc 5c 52`，且**每个 ZIP 局部头位置密文完全相同**（`fa cc 5c 52 72 5a 5e 4a`）→ 位置无关的**单字节变换**。

用已知明文反推映射：`50→fa, 4B→cc, 03→5c, 04→52, 14→72, 08→4a, 05→50, 06→56, 00→5a`，归纳出：

```
加密：c = rotl8(m, 1) ⊕ 0x5A      （循环左移 1 位再异或 0x5A）
解密：m = rotr8(c ⊕ 0x5A, 1)
```

验证 `fa⊕5a=a0`，右旋 1 位 = `50`='P' ✓。全文件解密后即合法 ZIP（16 条目，testzip 通过），读 `word/document.xml`：

**明文内容 = `42035533`**。

```python
data = open('cipher.docx','rb').read()
dec = bytes(((b ^ 0x5A) >> 1 | ((b ^ 0x5A & 1) << 7)) & 0xFF for b in data)
open('plain.docx','wb').write(dec)   # 然后当 docx 打开
```

> **思路回放（含被排除的弯路）**：① 报"损坏"第一步永远看文件头——`fa cc 5c 52 ≠ 50 4B 03 04`，但文件大小正常、结尾 EOCD 结构还在 → 是被加密不是损坏；② 先按"周期 XOR"假设做已知明文攻击：头部 + EOCD 的 6 个已知零字节反推密钥流，p=16 时锚点自洽但解出的文件名是乱码；再做频数攻击（各残差类众数峰），完全平坦 → **任何周期的重复密钥 XOR 全部排除**；③ 关键转折：全文件扫描 `fa cc`（`50 4B` 的密文形态），17 个局部文件头的密文**一字不差** → 变换与位置无关，是单字节映射；④ 收集明密对（50→fa、4B→cc、03→5c、08→4a、00→5a…），加法差、XOR 差都不齐，改看**位结构**：x=1↔差 0x02、x=2↔差 0x04、x=4↔差 0x08 → 左移 1 位，再补常数 0x5A；⑤ 全文件解密 → `zipfile` 直接打开（testzip 通过）→ 读 document.xml。

**坑位清单**：不需要 binwalk/foremost 之类的杂项提取工具；判断顺序是 ① 看文件头是否还是 ZIP/OLE → ② 不是则找"位置无关变换"（同一结构位置密文相同）→ ③ 单字节替换/移位/异或逐个试，用 `50 4B 03 04` 当已知明文锚。若变换是位置相关的（多字节 XOR 流），才需要密钥流分析。

## 第四题（实操 250 分）：MD5 口令破译 + 系统登录

### 题目

截获的明文/密文口令对（数据库存 MD5(Pass)）：

| 用户名 | 明文口令 | 密文 |
|---|---|---|
| alice | 123456 | e10adc3949ba59abbe56e057f20f883e |
| bob | abcdef | e80b5017098950fc58aad83c8c14978e |
| charlie | qwerty | d8578edf8458ce06fbc5bb76a58c5ca4 |
| dave | secret | 5ebe2294ecd0e0f08eab7690d2a6ee69 |

admin 的加密口令 `aa6490394ce8565612fd2d55f346fb7c`，已知口令为 6 位数字。破译后登录 `172.16.8.6:80` 获取 FLAG（15 位数字）。

### 解析

先用四组明密对确认算法就是纯 `MD5(Pass)`（无加盐/变形）。6 位数字空间只有 10⁶，直接掩码暴力：

```bash
# hashcat：-m 0 = MD5，-a 3 = 掩码，?d = 数字
hashcat -m 0 -a 3 aa6490394ce8565612fd2d55f346fb7c ?d?d?d?d?d?d
```

> **思路回放**：四组明密对先验算法——`MD5("123456")` 等逐一对上 → 确认纯 MD5、无盐无变形（这一步决定 hashcat 的 `-m` 参数）；再看约束"6 位数字" → 搜索空间仅 10⁶，掩码 `?d?d?d?d?d?d` 一把梭，hashcat 与 Python 循环都是秒级；FLAG 不在本地，登录 Web 后才发放。

**答案：admin 口令 = `770713`**（秒出）。浏览器登录 172.16.8.6 输入口令即得 15 位数字 FLAG（值随环境，本复盘时平台未开放，提交以现场为准）。

## 备赛要点（真题复盘总结）

1. **答案格式**：十进制串直接交，别画蛇添足 `.decode()`/`flag{}`。
2. **RSA 三板斧**：φ(p²q)=p(p−1)(q−1)；`gcd(n₁,n₂)` 共享因子；解出来"太小"的整数就是答案本身。
3. **国密流量**：认准 record 版本 `0x0101`、套件号 0xE011=ECDHE / 0xE013=ECC；看 CertificateRequest + 客户端 Certificate/CertVerify 判单向/双向；CKE 里的 65B `04‖X‖Y` 是协商预主密钥的核心数据。魔数非 `d4c3b2a1` 的 pcap 要手工切包。
4. **文件加密**：先验文件头（`50 4B 03 04`/`D0 CF 11 E0`），同一结构偏移密文相同 → 位置无关单字节变换，用已知文件头反推映射。
5. **口令破译**：先拿明密对验算法（纯 MD5 vs 加盐/HMAC），再用 hashcat 掩码按已知长度暴力。
