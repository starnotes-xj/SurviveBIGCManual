# 上半场（8 题 · 100 分）

### S4-A1 维吉尼亚密码 ★（10 分）

截获密文：`KJARBGITIHJAQKHWV`
已知密钥为 `ISCC`，字母表 A=0…Z=25，加密方式为逐字母移位（第 i 个字幕用密钥第 `i mod 4` 个字母移位）。

**任务**：恢复明文（全大写，无空格）。

**所需知识**：多表替换密码、维吉尼亚方阵、密钥循环使用、模 26 运算

??? tip "答案与解析"
    **答案：`CRYPTOGRAPHYISFUN`**

    ```python
    def vig_dec(ct, key):
        out, ki = [], 0
        for ch in ct:
            out.append(chr((ord(ch) - 65 - (ord(key[ki % len(key)].upper()) - 65)) % 26 + 65))
            ki += 1
        return ''.join(out)

    vig_dec('KJARBGITIHJAQKHWV', 'ISCC')   # 'CRYPTOGRAPHYISFUN'
    ```

    考点：维吉尼亚是"多表替换"，同一个明文字母在不同位置会变成不同密文，因此**单表频率分析失效**。破解思路是先用 Kasiski 测试 / 重合指数（IC）求出密钥长度，再对每个位置单独做凯撒频率分析。

### S4-A2 异或 + Base64 ★（10 分）

某程序用循环异或加密后再 Base64 编码。已知密钥 `iscc2026`，密文：

```
Dx8CBElIXUQ2EQIQVwYGaQocDgFdTQ==
```

**任务**：解出明文（flag 格式）。

**所需知识**：XOR 的自反性（a⊕k⊕k=a）、循环密钥、Base64 编码原理、Python bytes 操作

??? tip "答案与解析"
    **答案：`flag{xor_base64_combo}`**

    ```python
    import base64
    key = b'iscc2026'
    ct = base64.b64decode('Dx8CBElIXUQ2EQIQVwYGaQocDgFdTQ==')
    print(bytes(c ^ key[i % len(key)] for i, c in enumerate(ct)))
    # b'flag{xor_base64_combo}'
    ```

    提醒：**顺序不能反**——必须先去 Base64 再异或。看到 base64 字符集（含 `+` `/` `=`）先解一层是固定动作。

### S4-C1 密钥库信息提取 ★（10 分）

拿到一个 Java 密钥库 `server.jks`，口令 `changeit`。

**任务**：写出查看库中所有条目别名的命令，并说明如何导出某个条目的证书。

**所需知识**：JKS/PKCS#12 密钥库格式、keytool 子命令、别名与条目类型（PrivateKeyEntry/TrustedCertEntry）

??? tip "答案与解析"
    ```bash
    # 列出所有条目
    keytool -list -v -keystore server.jks -storepass changeit

    # 导出指定别名条目的证书（DER 格式）
    keytool -exportcert -alias myserver -keystore server.jks -storepass changeit -file myserver.cer -rfc
    ```

    要点：
    - `-rfc` 输出 PEM（Base64）格式，不加则输出二进制 DER；
    - `-list -v` 会打印证书链、有效期、签名算法——**审计时重点看签名算法是否为 SHA1withRSA/MD5withRSA（不合规）**；
    - 口令写在命令行会被 `history` 记录，实战中应改用 `-storepass:file` 或交互输入。

### S4-D1 算法合规速判 ★（10 分）

某政务系统清单如下，判断每项是否满足商用密码应用要求（合规 / 不合规）：

① SM4-CBC 加密数据库字段 ② SM3 做文件完整性校验 ③ MD5 存用户口令
④ RSA-2048 签名 ⑤ SM2 签名 ⑥ AES-128-GCM 加密传输
⑦ DES 加密配置 ⑧ SHA-1 做日志防篡改

**任务**：给出每项的判断，并说明"国密算法"与"国际算法"在密评中的定位。

**所需知识**：国密算法族、算法强度要求、GB/T 39786-2021、《密码法》对核准算法的规定

??? tip "答案与解析"
    | 项 | 判断 | 理由 |
    |---|---|---|
    | ① SM4-CBC | 合规（建议加完整性保护） | 国密分组算法，128 位强度足够；CBC 无完整性校验，宜配 HMAC 或用 GCM |
    | ② SM3 | 合规 | 国密杂凑，256 位 |
    | ③ MD5 存口令 | **不合规** | MD5 已破，且裸哈希无盐 |
    | ④ RSA-2048 签名 | 一般可接受，密评中**不推荐** | 强度够，但政务/密评场景应优先 SM2 |
    | ⑤ SM2 签名 | 合规（推荐） | 国密非对称，具备不可否认性 |
    | ⑥ AES-128-GCM | 强度合规，但密评场景**宜改 SM4** | GCM 是 AEAD，安全性好；合规性看具体项目要求 |
    | ⑦ DES | **不合规** | 56 位密钥可暴力破解 |
    | ⑧ SHA-1 | **不合规** | 已可构造碰撞 |

    **定位**：密评（GB/T 39786）要求使用**国家密码管理部门核准的算法**。SM 系列是"应当优先采用"，国际算法（AES/RSA/SHA-256）安全性上不弱，但在**等保/密评的合规判定**里，国密是默认答案。答题时把"技术安全"和"合规"分开说，两者不是一回事——这也是密码安全赛最容易被扣分的地方。

### S4-B1 TOTP 动态口令 ★★（15 分）

某 VPN 用 TOTP（RFC 6238）做二次验证：

```
密钥（Base32）: JBSWY3DPEHPK3PXP
时间步长    : 30 秒
位数        : 6
基准时间 T0 : 0（Unix epoch）
```

**任务**：求 `T = 1735689600` 这一时刻的动态口令，并说明服务器通常接受几个时间窗口。

**所需知识**：HOTP/TOTP 算法（RFC 4226/6238）、HMAC-SHA1、动态截断（DT）、时间步长与窗口容错、Base32 解码

??? tip "答案与解析"
    **答案：`768725`**（该时刻的 counter = 1735689600 ÷ 30 = 57856320）

    ```python
    import hmac, hashlib, base64, struct

    def hotp(key, counter, digits=6):
        h = hmac.new(key, struct.pack('>Q', counter), hashlib.sha1).digest()
        o = h[-1] & 0x0f                                  # 动态截断偏移
        return str((struct.unpack('>I', h[o:o+4])[0] & 0x7fffffff) % 10**digits).zfill(digits)

    key = base64.b32decode('JBSWY3DPEHPK3PXP')
    hotp(key, 1735689600 // 30)          # '768725'
    hotp(key, 1735689600 // 30 + 1)      # '651134'，下一时刻
    ```

    服务器通常接受 **±1 个时间窗**（即当前、前一个、后一个 30 秒，共 90 秒），用于容忍时钟漂移。窗口开得越大，被重放的风险越高——所以 TOTP 必须**一次性使用**（用过即作废），否则在窗口内可重放。

### S4-E1 功耗分析 ★★（15 分）

某智能卡执行 AES 时，攻击者采集了 10 万条功耗曲线，发现同一条曲线上不同时刻的峰值与"当前处理的密钥字节"存在相关性。

**任务**：区分这是 SPA 还是 DPA，说明两者原理差异、各自能恢复什么，以及常见防御。

**所需知识**：简单功耗分析（SPA）、差分功耗分析（DPA）、汉明重量/汉明距离模型、掩码与隐藏技术、功耗与数据相关性

??? tip "答案与解析"
    **这属于 DPA（差分功耗分析）**，不是 SPA。

    | | SPA | DPA |
    |---|---|---|
    | 原理 | 直接目视单条曲线的功耗模式，识别指令序列（如平方-乘序列暴露 RSA 私钥比特） | 对大量曲线按猜测密钥分组求平均，用统计相关性放大极小差异（如汉明重量模型） |
    | 曲线数 | 几条到几十条 | 数千到数十万条 |
    | 能恢复 | 算法流程、分支走向（间接泄露私钥） | 密钥字节本身（逐字节爆破，每次只需 256 种假设） |
    | 典型目标 | RSA 模幂、条件跳转 | AES S 盒输出的汉明重量 |

    **防御**：
    - **隐藏（hiding）**：随机插入延时、双轨预充电逻辑、功耗均衡电路——让功耗与数据无关；
    - **掩码（masking）**：把中间值拆成 `x ⊕ m` 两段分别计算，单点功耗不再与 x 相关（需注意二阶 DPA）；
    - **算法层**：恒定时间实现、避免数据相关分支与查表索引。

### S4-F1 密码重置令牌 ★★（15 分）

某站点重置密码的链接为：

```
https://example.com/reset?token=5f3c8a1e9b2d4f6a&uid=1001
```

审计发现：token 为 16 位十六进制，由 `md5(uid + 固定后缀)` 生成；链接 24 小时内有效，可重复使用。

**任务**：指出至少 3 个安全问题，并说明最严重的那个如何导致账户接管。

**所需知识**：随机数熵、可预测令牌、一次性使用与失效、越权（IDOR）、令牌绑定用户与会话

??? tip "答案与解析"
    **问题清单：**

    1. **令牌可预测**：`md5(uid + 固定后缀)` —— 后缀固定意味着同一 uid 的令牌**永远相同**，且 md5 无密钥，攻击者拿到一个样本即可对任意 uid 推算（等价于"无随机性"）。16 位十六进制只有 64 bit，若含真实随机也偏短。
    2. **可重复使用 / 24 小时过长**：令牌用后不失效，一旦泄露（邮件转发、日志、浏览器历史、Referer 泄露）可长期利用。
    3. **uid 明文可控（IDOR）**：`uid` 作为独立参数，攻击者可改 uid 为管理员，配合可预测的令牌直接重置管理员口令 —— **这就是账户接管路径**。
    4. **令牌未绑定会话/未校验来源**：无 referer 或会话校验，可被 CSRF 式诱导。

    **最严重**：①+③ 组合。因为令牌由 uid 确定性派生，攻击者只需知道目标 uid（通常是自增整数），算出 `md5(uid + 后缀)` 即可构造合法重置链接 → 直接接管任意账户，包括管理员。

    **修复**：用 CSPRNG 生成 ≥128 bit 随机令牌，**服务器端存储哈希**、绑定 uid、一次性使用、15 分钟内过期、用后立即作废并通知用户。

### S4-A3 PBKDF2 迭代次数 ★★（15 分）

某系统用 `PBKDF2-HMAC-SHA256(password, salt, N, 32)` 派生密钥，`salt = "isccsalt"`，`password = "password"`。
截获两个派生结果：

```
A: 0389d777ec28a5ee92b0ac5b506a76f2d4d16e208fae4145b5794a2ebe0abb73
B: 84d3eb4fe65bf0c12cb9a476aee8afce4efbcdbc81c1fccfae6d348d197f01f0
```

**任务**：判断哪个结果的迭代次数更高，并算出 A 对应的迭代次数（候选：1 / 1000 / 10000）。

**所需知识**：PBKDF2 结构与迭代、HMAC、慢哈希的抗爆破原理、GPU/ASIC 爆破代价、盐的作用

??? tip "答案与解析"
    **A 的迭代次数 N = 1**（`pbkdf2_hmac('sha256', b'password', b'isccsalt', 1, 32)` 直接得到 A）；B 对应 N = 1000。

    ```python
    import hashlib
    hashlib.pbkdf2_hmac('sha256', b'password', b'isccsalt', 1, 32).hex()
    # 0389d777ec28a5ee92b0ac5b506a76f2d4d16e208fae4145b5794a2ebe0abb73
    hashlib.pbkdf2_hmac('sha256', b'password', b'isccsalt', 1000, 32).hex()
    # 84d3eb4fe65bf0c12cb9a476aee8afce4efbcdbc81c1fccfae6d348d197f01f0
    ```

    **N=1 等于没做慢哈希**：PBKDF2 的意义在于把"一次哈希"放大成 N 次，让攻击者每次猜测的代价乘以 N。N=1 时 GPU 每秒可试上百亿次，与裸 SHA-256 无异。

    工程取值：OWASP 建议 PBKDF2-HMAC-SHA256 至少 **600,000 次**（2023 起）；NIST SP 800-63B 只要求"够慢"。同时**盐必须每用户随机且足够长**（≥16 字节）——本例 `isccsalt` 是固定盐，两个用户口令相同则派生结果相同，等于没有盐。

**任务**：恢复明文（flag 格式）。

**所需知识**：中国剩余定理（CRT）、RSA 低指数广播攻击（Håstad）、整数开立方根、互素模数的合并

??? tip "答案与解析"
    **答案：`flag{three_moduli_crt_attack}`**

    e=3 且三组密文对应同一明文时，`m³` 分别落在三个不同的模数下；用 CRT 可还原出 `M = m³ mod (n1·n2·n3)`。由于 `m³` 只有 693 位而 `n1·n2·n3` 有 1536 位，`m³ < n1·n2·n3`，所以 **CRT 结果就是 m³ 本身**，直接开立方根即得明文。

    ```python
    def crt(rs, ms):
        M = 1
        for m in ms: M *= m
        return sum(r * (M // m) * pow(M // m, -1, m) for r, m in zip(rs, ms)) % M

    def iroot3(x):
        lo, hi = 0, 1 << (x.bit_length() // 3 + 2)
        while lo < hi:
            mid = (lo + hi + 1) // 2
            if mid**3 <= x: lo = mid
            else: hi = mid - 1
        return lo

    M = crt([c1, c2, c3], [n1, n2, n3])
    iroot3(M).to_bytes(29, 'big')     # b'flag{three_moduli_crt_attack}'
    ```

    **识别特征**：题目给"同一个 e、多个 n、多个 c"→ 先想广播攻击（Håstad）。与之易混的是**共模攻击**（同一个 n、多个 e），别搞反：**同 n 同 e 混淆、同 e 多 n 广播**。

    防御：e 用 65537，且加密前对明文做 OAEP 填充（使每次加密结果随机化）。

    **SageMath 解法**（10.9 实测）：`crt` + `nth_root` 两行：

    ```python
    MM = crt([c1, c2, c3], [n1, n2, n3])
    m, exact = Integer(MM).nth_root(3, truncate_mode=1)
    print(m.to_bytes(29, 'big').decode())           # flag{three_moduli_crt_attack}
    ```

### S4-A5 ECDSA 相关随机数攻击 ★★★（25 分）

secp256k1 上，同一私钥 `d` 对两条消息签名，**复用了同一个随机数 k**，得到相同的 `r`：

```
r  = 0x200c9e9b2efecdb877fee50884729f6a5bc0edaf7541f14981dbe2515ad54db3

消息1: "ISCC 2026 pay 100 to bob"
  z1 = 830967d5cb4bf527bcd79bb26e1aba55bdc5f49f06611db31f19ac7900b0575f
  s1 = 0xba39b25d05de61280607260cd71133179103a41d654ea25e4268754222ca6a93

消息2: "ISCC 2026 pay 900 to bob"
  z2 = 7bdda533834306c8770e6c421b9d90d6090abc9f7c191f9b1c63f4c2298bbef8
  s2 = 0x32af4d147fb6c46d27290e237ed54b596adba31168ad83218ad7c1ff0008f28f
```

（z 为消息 SHA-256 的整数解释，secp256k1 阶 n 为曲线阶。）

**任务**：恢复私钥 d（十六进制）。

**所需知识**：ECDSA 签名方程 s = k⁻¹(z + rd)、随机数复用的代数推导、模 n 求逆、secp256k1 参数

??? tip "答案与解析"
    **答案：`0x3f8a1b2c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f708192a3b4c5d6e7f8`**

    推导：同一 k 下
    ```
    s1 = k⁻¹(z1 + r·d)
    s2 = k⁻¹(z2 + r·d)
    ```
    两式相减消去 d：
    ```
    s1 - s2 = k⁻¹(z1 - z2)
    → k = (z1 - z2) / (s1 - s2)  mod n
    → d = (s1·k - z1) / r        mod n
    ```

    ```python
    n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
    r  = 0x200c9e9b2efecdb877fee50884729f6a5bc0edaf7541f14981dbe2515ad54db3
    z1 = 0x830967d5cb4bf527bcd79bb26e1aba55bdc5f49f06611db31f19ac7900b0575f
    z2 = 0x7bdda533834306c8770e6c421b9d90d6090abc9f7c191f9b1c63f4c2298bbef8
    s1 = 0xba39b25d05de61280607260cd71133179103a41d654ea25e4268754222ca6a93
    s2 = 0x32af4d147fb6c46d27290e237ed54b596adba31168ad83218ad7c1ff0008f28f

    k = (z1 - z2) * pow(s1 - s2, -1, n) % n
    d = (s1 * k - z1) * pow(r, -1, n) % n
    hex(d)   # 0x3f8a1b2c...d6e7f8
    ```

    这道题的价值：**同一 r 出现两次就是致命的**。历史上 PlayStation 3（2010）、索尼、以及大量区块链钱包都栽在 k 复用或 k 偏短（格攻击）上。防御：用 RFC 6979 确定性 k，或硬件 CSPRNG。

### S4-B2 TLS 1.3 密钥调度 ★★（20 分）

TLS 1.3 用 HKDF 从共享秘密派生出多个密钥。

**任务**：说明 TLS 1.3 为什么要用 `HKDF-Extract` + `HKDF-Expand` 两步而不是直接哈希，并指出客户端与服务端各自使用哪组密钥、握手密钥与主密钥的关系。

**所需知识**：HKDF（Extract 提取熵 / Expand 扩展输出）、TLS 1.3 密钥调度图、Early/Handshake/Application 三层密钥、AEAD 与 nonce 构造、前向保密

??? tip "答案与解析"
    **为什么两步**：`HKDF-Extract(salt, IKM) = HMAC(salt, IKM)` 的作用是把任意长度、任意分布的输入（如 ECDHE 共享秘密，可能不完全均匀）**压缩成固定长度的伪随机密钥 PRK**，把"熵提取"与"输出扩展"分开；`HKDF-Expand(PRK, info, L)` 再用不同的 `info` 标签派生出**多个互相独立**的密钥。直接哈希有两个问题：不能保证输出均匀分布、且一次哈希很难安全地派生出多把用途不同的密钥。

    **TLS 1.3 的三层密钥**：
    ```
    PSK / (EC)DHE  →  Early Secret  →  client_early_traffic_secret
                    →  Handshake Secret → client/server_handshake_traffic_secret
                    →  Master Secret  →  client/server_application_traffic_secret_0
    ```
    每一层都用 `HKDF-Extract` 把上一层的 secret 与新的输入（DHE 共享秘密）混合，所以**握手完成时 Early Secret 的熵已被完全替换**——这就是前向保密的来源。

    **方向分离**：`client_*` 与 `server_*` 是两条独立派生链，各自再用 `HKDF-Expand-Label(secret, "key"/"iv", ...)` 得到 AEAD 的 key 和 IV。**两个方向密钥不同**，避免反射攻击与 nonce 碰撞。

    **答题要点**：Extract 保熵、Expand 做域分离（domain separation）、三层 secret 逐步混入新熵、双向密钥独立。

### S4-C2 AES-GCM 的 nonce 复用 ★★★（20 分）

某系统用 AES-256-GCM 加密网络报文，nonce 由**全局计数器**生成，但服务重启后计数器**从 0 重新开始**，且历史 nonce 未持久化。

**任务**：说明这会造成什么后果、攻击者能推出什么，并给出两种修复方案。

**所需知识**：GCM 的 CTR 流加密本质、GHASH 认证、nonce 唯一性要求、密钥流复用（two-time pad）、认证密钥恢复

??? tip "答案与解析"
    **GCM = CTR 加密 + GHASH 认证**，两者都依赖 nonce 唯一。

    **后果一：明文泄露（密钥流复用）**
    GCM 的加密部分是 `C = P ⊕ KS(nonce, counter)`。同一密钥 + 同一 nonce → **完全相同的密钥流**，于是
    ```
    C1 ⊕ C2 = P1 ⊕ P2
    ```
    攻击者得到两条密文的异或，等于两条明文的异或。若其中一条明文已知（协议头、固定字段、纯文本），另一条即被完全还原。这就是"两次一密"（two-time pad）。

    **后果二：认证密钥被恢复（更严重）**
    GCM 的认证标签由 GHASH 用 `H = AES_K(0^128)` 计算。同一 nonce 下出现两组 (C, T)，攻击者可建立关于 H 的方程组，**代数地解出 H**；掌握 H 后即可对**任意**密文伪造合法标签——完整性彻底失守，且影响的不只是重复的那两条报文。

    **修复**：
    1. **持久化计数器**：重启后从上次值继续（写入非易失存储并原子递增），或直接用**随机 96 bit nonce**（碰撞概率可忽略）；
    2. **每次会话换密钥**：用 HKDF 从主密钥 + 会话 ID 派生每会话子密钥，子密钥内计数器从 0 开始也安全；
    3. 附加：限制单密钥加密的报文数量（GCM 对单密钥有 2³² 量级的安全上限）。

    **一句话**：AEAD 不是"加了认证就万事大吉"——**nonce 复用对 GCM 是灾难级的**，比 CBC 的 IV 复用严重得多。

### S4-D2 密评三级要求 ★★（20 分）

某等保三级系统要做商用密码应用安全性评估（密评）。

**任务**：说明密评的"四性"分别对应哪些密码技术，并指出三级系统在"身份鉴别"和"数据完整性"两个层面的典型要求。

**所需知识**：GB/T 39786-2021 三级要求、四性（机密性/完整性/真实性/不可否认性）、密码技术与管理措施的对应、密评流程

??? tip "答案与解析"
    **四性 → 技术映射：**

    | 性质 | 目标 | 典型密码技术 |
    |---|---|---|
    | **机密性** | 数据不被未授权读取 | SM4 加密（存储/传输）、SM2 密钥交换 |
    | **完整性** | 数据未被篡改 | SM3 杂凑、HMAC-SM3、SM2 签名 |
    | **真实性** | 身份与来源可信 | SM2 数字证书、动态口令、SM9 标识认证 |
    | **不可否认性** | 行为不可抵赖 | SM2 数字签名 + 可信时间戳 |

    **三级系统的典型要求：**
    - **身份鉴别**：对登录用户采用**两种或两种以上**组合的鉴别技术（如口令 + 智能密码钥匙/动态令牌/生物特征），且鉴别信息传输与存储须加密；远程管理必须使用密码技术建立安全通道。
    - **数据完整性**：重要数据在**传输和存储**两个环节都要有完整性保护（SM3/HMAC-SM3 或签名）；且要能**检测到**篡改，而非仅"防误码"。

    **答题框架**：密评 = "**技术 + 管理**"双维度。技术看四性有没有落地、算法是否合规；管理看**制度、人员、密钥管理、应急预案**是否齐备。只答技术最多拿一半分。

### S4-E2 缓存计时攻击 ★★（20 分）

某服务端用 AES 软件实现，S 盒查表按索引访问内存。攻击者与目标共享物理机（同云主机/同容器宿主），可通过 `clflush` + `rdtsc` 测量缓存命中时间。

**任务**：说明这类攻击的原理、能恢复什么、以及在云环境中的现实性与防御。

**所需知识**：缓存层次与访问延迟、Flush+Reload / Prime+Probe、缓存侧信道、常量时间实现与位切片、SGX/TrustZone 相关攻击

??? tip "答案与解析"
    **原理**：AES 的 S 盒查表索引依赖密钥（`S[state ⊕ roundkey]`）。若攻击者能观察到"哪些缓存行被访问"，就得到了索引的部分信息，进而反推密钥字节。

    **两种典型手法：**
    - **Flush+Reload**：攻击者 `clflush` 掉整个 S 盒（共享内存页，需同物理页/去重），让受害者加密，再逐个探测 S 盒每个缓存行的访问时间——**被访问过的行更快**，由此得到索引集合；
    - **Prime+Probe**：不需要共享内存，攻击者用自己的数据占满 LLC 的组（prime），受害者运行后再测量自己哪些组变慢（probe），推断其访问模式。

    **能恢复什么**：AES 密钥（最后一轮尤甚，因为末轮无 MixColumns，索引与密钥字节直接相关），通常需要数万到数百万次采样。

    **现实性**：在公有云**同宿主机**、容器共享 CPU 缓存、以及 SGX 飞地场景下都已被实证（如 2017 年的 SGX 攻击、多个云上 AES 侧信道研究）。跨物理机不成立。

    **防御**：
    - **算法层**：改用 **AES-NI 硬件指令**（查表在 CPU 内部，不走数据缓存）或**位切片/恒定时间软件实现**（无数据相关索引）；
    - **系统层**：缓存着色（cache coloring）、关闭内存去重（KSM）、避免同宿主机混布敏感负载；
    - 实践中最有效的一条：**不要在软件里用查表实现 AES**。

### S4-F2 加密 Cookie 的会话固定 ★★（20 分）

某站把会话信息加密后放 Cookie：

```
Set-Cookie: sess=<base64(AES-ECB(session_id|user_id|role))>
```

登录前后使用**同一个** Cookie 值，服务端解密后直接信任其中的 `role` 字段。

**任务**：指出至少 3 个缺陷，并说明"仅把 ECB 换成 CBC + 随机 IV"能否解决问题。

**所需知识**：会话管理、Cookie 属性（HttpOnly/Secure/SameSite）、ECB 与块重排、AEAD 与完整性保护、客户端存储的信任边界

??? tip "答案与解析"
    **缺陷：**

    1. **信任客户端可控数据**：角色（role）从 Cookie 解出即用，等于把授权决策交给客户端。加密只保证"看不懂"，不保证"改不了"——尤其 ECB 与无 MAC 的 CBC 都可被操纵。
    2. **ECB 可块重排/拼接**：同一明文块产出同一密文块，攻击者可把管理员会话的某块拼进自己的 Cookie。
    3. **会话固定（Session Fixation）**：登录前后 Cookie 不变，攻击者预先把自己的 sess 值投喂给受害者（URL 参数、子域 Cookie 注入），受害者登录后该会话即带上了受害者身份，攻击者直接复用。
    4. **缺少 HttpOnly / Secure / SameSite**：可被 XSS 读取、明文信道泄露、CSRF 携带。
    5. **无过期与轮换**：长期有效，泄露后无法收回。

    **换成 CBC + 随机 IV 能解决吗？——不能。**
    CBC 只解决"块重排看结构"，但：
    - 没有 MAC 时，CBC 可被**比特翻转**（改前一块密文即可定向改明文）；
    - 缺少完整性保护意味着任何"加密但可塑"的容器都不安全；
    - 会话固定、信任客户端 role、Cookie 属性缺失**都不是加密模式能修的**。

    **正确做法**：
    - 会话状态放**服务端**，Cookie 只放不可预测的随机 session id（≥128 bit）；
    - 若确实要放客户端，用 **AEAD（AES-GCM / SM4-GCM）**，并把 user_id 与 role 一并认证；服务端仍需校验权限，不能只信 Cookie；
    - 登录成功**必须轮换 session id**（防固定）；
    - 加 `HttpOnly; Secure; SameSite=Lax`，设置合理过期与空闲超时。

### S4-F3 口令存储方案设计 ★★（20 分）

为某系统设计口令存储方案。约束：日活 10 万、单机可接受 50 ms 的登录延迟、有国密合规要求、需支持后续算法升级。

**任务**：给出完整方案（算法、盐、参数、存储格式、升级策略），并说明如何抵抗离线爆破与彩虹表。

**所需知识**：慢哈希与工作因子、每用户随机盐、pepper（应用级密钥）、算法敏捷性/版本化存储、国密合规（SM3/PBKDF2）、时序安全比较

??? tip "答案与解析"
    **推荐方案（国密合规版）：**

    ```
    存储格式（版本化，便于将来升级）：
    $pbkdf2-sha256$v=1$i=600000$<base64(salt)>$<base64(dk)>

    算法：PBKDF2-HMAC-SM3（若无 SM3 支持则 PBKDF2-HMAC-SHA256）
    盐  ：每用户 16 字节 CSPRNG 随机（secrets.token_bytes(16)）
    迭代：调参到单次约 50 ms（本机实测后取整；SM3 下通常 20 万～60 万次）
    pepper：全局密钥，存 KMS/HSM，不进数据库（HMAC(pepper, password) 后再入 PBKDF2）
    ```

    **抗彩虹表**：每用户随机盐 → 同一口令在不同用户下结果不同，预计算表失效。
    **抗离线爆破**：迭代次数把单次猜测成本放大 N 倍；pepper 让"拖库但未拿到 KMS 密钥"的攻击者无法离线爆破（**这是最关键的一层**）。
    **抗时序攻击**：比较用 `hmac.compare_digest`，不要用 `==`。

    **升级策略（算法敏捷性）**：
    1. 存储串里带**算法与参数版本**（如上 `v=1$i=600000`），不要写死在代码里；
    2. 登录成功时**顺带重算**：若记录的参数低于当前标准，用新参数重新派生并覆盖（渐进式升级，无需强制改密）；
    3. 保留旧算法校验路径，直到所有活跃用户都完成迁移。

    **加分点**：说明为什么不用裸 SHA-256（太快）、为什么 bcrypt 有 72 字节截断问题、为什么 Argon2id 更强但需评估合规要求。
